# Roadmap

Durable plan narrative for this repository: goals, phases, sequencing, and the reasoning behind the order. Each item
links its owning YouTrack issue. Status is read from the tracker, never restated here.

## Tactical RMM: configuration control and startup time

### Problem

The `tactical-backend` image ships the Django tree in `/tmp/tactical` and hydrates the runtime directory from it on
every start, with an `rsync --delete` in the upstream init block. Because that tree has to be visible to every service,
a single `tactical-data` volume is mounted at `/opt/tactical` on all nine application containers. Three consequences
follow:

- **Restarts take minutes.** The rsync, a recursive `chown` over the whole volume, and fourteen unconditional
  `manage.py` commands run on every start. Every other container then blocks on a ready file behind a flat `sleep 15`
  plus a 10 second poll.
- **uWSGI is slow to become useful.** `create_uwsgi_conf` sizes the worker pool from RAM alone with no CPU term, then
  the `busyness` cheaper algorithm climbs toward that ceiling gradually.
- **The three files an operator most needs to control cannot be controlled.** `app.ini` and `local_settings.py` are
  regenerated by the init block on every run, and MeshCentral's `config.json` is overwritten on every mesh start.
  `local_settings.py` also mints a fresh `SECRET_KEY` each time, so every restart invalidates every session.

The `TRMM_SETTING_*` mechanism in `tactical-rmm/backend/settings_env.py` exists as a workaround for the third point. It
stays, but it should not be the only durable override surface.

### Direction

Bake the application code at its final path in the image, mount only mutable state and configuration, and make
configuration seed-once rather than regenerate-always. `tactical-init` then shrinks to database work and is eventually
retired.

### Phases

1. [PIMP-53](https://niceguyit.myjetbrains.com/youtrack/issue/PIMP-53) - Bake the API tree into the backend image at
   `/opt/tactical/api`, delete the rsync and the recursive chown, and replace the single shared volume with five
   purpose-scoped ones (`conf`, `tmp`, `private`, `certs`, `reporting`). Fork the backend, frontend and nats entrypoints
   so the readiness waits can drop the `sleep 15`.
2. [PIMP-54](https://niceguyit.myjetbrains.com/youtrack/issue/PIMP-54) - Move `app.ini` and `local_settings.py` into a small
   `/opt/tactical/conf` directory that is seeded once and never overwritten, so it works as a named volume or a
   read-only host bind mount. Establishes the precedence chain `generated < conf/local_settings.py < TRMM_SETTING_*`
   and replaces `create_uwsgi_conf` with a shipped, commented `app.ini`.
3. [PIMP-55](https://niceguyit.myjetbrains.com/youtrack/issue/PIMP-55) - Flip `MESH_PERSISTENT_CONFIG` to default on, and render
   MeshCentral's `config.json` from a template file rather than an entrypoint heredoc.
4. [PIMP-56](https://niceguyit.myjetbrains.com/youtrack/issue/PIMP-56) - Record the layout revision and Tactical RMM version in the
   ready file, and run the heavy management commands only when that marker does not match the image.
5. [PIMP-57](https://niceguyit.myjetbrains.com/youtrack/issue/PIMP-57) - Remove the `tactical-init` service, folding migration and
   first-run seeding into the Django containers' startup behind a PostgreSQL advisory lock. The command name survives
   as a manual entry point for forced re-seeding.

### Why this order

PIMP-54 and PIMP-56 both need the baked layout from PIMP-53: there is no stable place to mount a conf directory while a
volume is mounted over the whole application tree, and version-gating the init work is pointless while an unconditional
rsync still runs ahead of it. PIMP-55 is independent in code but follows PIMP-54 so both persistence knobs land with the
same naming and the same seed-if-absent semantics. PIMP-57 comes last because removing the ready-file handshake is only
safe once the fast path from PIMP-56 exists and the seeding work is small enough to serialize on a lock.

### Breaking change

PIMP-53 changes the volume layout, and the published image tag tracks the upstream Tactical RMM version, so the tag
cannot signal the break. Mitigation is a build-time layout marker checked at startup, which aborts with a pointer to the
migration instructions when a legacy whole-directory mount shadows the image, plus a migration section in the README.
